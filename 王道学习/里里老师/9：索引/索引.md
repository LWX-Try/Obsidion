# 三：索引（重要，面试常用）
---
## 3.1：什么是索引
<font color="#ff0000">MySQL官方对索引的定义是：索引是可以帮助MySQL高效获取数据的数据结构。</font>
优点就是提高查询数据的速率。
## 3.2：索引底层数据结构
- 计算机组织数据的过程中，常见的数据结构有：
  <font color="#ff0000">链表类型线性表</font>，<font color="#ff0000">数组类型线性表</font>，<font color="#ff0000">栈</font>，<font color="#ff0000">队列</font>，<font color="#ff0000">二叉树</font>，<font color="#ff0000">二叉搜索树</font>，<font color="#ff0000">红黑树</font>，<font color="#ff0000">Hash表: key-> 计算数据存储位置; 非常不利于范围查找, hash冲突</font>，<font color="#ff0000">B树/B-树</font>，<font color="#ff0000">B+树</font>。
1. 数组：数组是连续的地址空间，如果使用数组存储索引，那么就需要非常大的连续的地址空间。
2. 链表：链表虽然解决了连续地址空间的问题，但是链表中的元素往往不是有序的，所以不适合作为索引。
3. 哈希：查找速率非常快（暂不考虑哈希冲突），但是不太合适范围查找。
4. 树：如果是二叉树，那么数据的条数比较多，那么索引也会比较多，那么如果使用二叉树，就会导致树的高度是非常高的，那么进行查询的时候就需要进行多次的磁盘IO。
5. B树：多叉树，可以解决上述几乎全部问题。可以解决地址连续的问题，查找速率的问，以及磁盘IO的次数问题。
6. B+树：B+树，在B树的基础上，会将叶子节点使用链表连接起来，这样就会更好的进行范围查找。
<font color="#ff0000">总结：MySQL中索引的底层数据结构是B+树。</font>
## 3.3：存储引擎在索引上的区别
索引总体分为<font color="#ff0000">主键索引，非主键索引。</font>
主键索引：<font color="#ff0000">以主键创建的索引，就是主键索引。只要创建了主键，就会自动生成主键索引树。</font>
非主键索引：<font color="#ff0000">以非主键创建的索引树；包括：唯一索引、普通索引、联合索引（组合索引）（多个列合在一起作为索引）</font>。
1. MyISAM存储引擎是5.5以前的默认存储引擎；不支持事务、支持表级锁、不支持外键；在MySQL8.0以后，会对MyISAM存储引擎的表有三个文件：<font color="#ff0000">.myd结尾存储的是数据文件、.myi结尾存储的是索引文件、.sdi存储的是表的结构文件</font>；也是就是说：<font color="#7030a0">MyISAM存储引擎会有三个文件，数据与索引是分开存放的。</font>
2. InnoDB存储引擎是5.5以及5.5以后默认的存储引擎；支持事务、支持行级锁，也支持表级锁、支持外键；在MySQL8.0以后，<font color="#ff0000">对于InnoDB存储引擎的表，只有一个文件：.ibd既存储数据、也存储索引还存储结构文件</font>；也就是说：<font color="#7030a0">InnoDB存储引擎的数据文件与索引文件是一起存放的。</font>
注意：要查找的文件在/var/lib目录下，有一个文件叫做mysql，但是不能以普通用户登录，需要提升为root用户才能登录。

### 3.3.1：MyISAM存储引擎
- 使用MyISAM存储引擎存储的表和表中数据的文件由三个文件组成： <font color="#ff0000">(/var/lib/mysql/)</font>
![[MyISAM存储的文件组成.png]]
1. .sdi文件: 表的结构定义文件
2. .MYD文件: 数据文件
3. .MYI文件: 索引文件
- <font color="#ff0000">注意：在MySQL8.0之前，不论事MyISAM存储引擎还是InnoDB存储引擎，都会有一个专门存储表结构的.frm文件，但是在MySQL8.0开始，删除了这个文件(这个在面试过程中容易被问到，因为有些公司还是基于MySQL5.7开发)。</font>
#### 3.3.1.1：主键索引
- 所谓主键索引, 就是把主键作为索引。
![[主键索引.png]]
在MyISAM中，通过主键索引访问的叶子上存储结果，不是一条一条数据，<font color="#ff0000">而是数据的物理地址</font>。
- <font color="#ff0000">通过主键访问到的结果是主键对应的数据和一个地址。这个地址指向的就是源数据。</font>
#### 3.3.1.2：非主键索引
所谓非主键索引, 就是把非主键设置为索引。
![[非主键索引.png]]
在MyISAM中，通过<font color="#ff0000">非主键索引</font>访问的叶子上存储结果，不是一条一条数据，和其主键索引一样<font color="#ff0000">也是数据的物理地址</font>。
### 3.3.2：InnoDB存储引擎
使用InnoDB存储引擎存储的表的文件由一个文件组成：
![[InnoDB存储的文件组成.png]]
- .ibd文件：包揽一切，存储表结构、数据、索引等
- 虽然InnoDB只有一个.idb文件，但是并不意味着只能放一颗B+树，文件内部逻辑上被划分了多个独立的段，每个B+树占用着一个段，相互分离。
  InnoDB 的表空间（`.ibd`）是一个逻辑存储容器，它的结构层次是：
  1. **页（Page）**：最小的存储单元（默认 16KB）。B+树的每个节点就是一个页。
  2. **区（Extent）**：由连续的 64 个页组成（约 1MB）。为了管理方便，空间是按区分配的。
  3. **段（Segment）**：**由若干个区组成，每个段专门服务于一个特定的索引或数据结构。**
**关键结论**：**你的主键索引（聚簇索引）是一个段，你建的每个辅助索引（普通索引、唯一索引）也都是独立的段。** 它们都在同一个 `.ibd` 文件里，但互不干扰地申请和占用各自的磁盘空间。
#### 3.3.2.1：主键索引
在InnoDB中的主键索引是和MyISAM中的主键索引不同的，<font color="#ff0000">在InnoDB中通过主键索引访问的最终的叶子上的结果是数据本身。</font>
![[InnoDB主键搜索.png]]
#### 3.3.2.2：非主键索引
![[InnoDB非主键搜索.png]]
- 在InnoDB中, 通过<font color="#ff0000">非主键索引</font>访问的叶子上存储的结果是<font color="#ff0000">主键索引的值</font>，也就是说<font color="#ff0000">无法获取完整的数据</font>，那么就需要<font color="#ff0000">回表</font>。所以回表的含义是：<font color="#ff0000">使用非主键索引查找不到需要的数据，但是可以查找到主键，然后通过主键索引再次查找，即可找到需要的数据，这个过程就是回表。</font>
- 思考问题：对于InnoDB而言，使用非主键索引进行数据查询，是不是一定需要回表。如果使用非主键索引查找的字段正好在索引上，就可以直接找到，就不需要回表，这个叫做索引覆盖，否则就要回表。
- 回表的效率比较低，能避免就避免。索引覆盖效率略高。
## 3.4：索引相关语法
```
#主键索引
#在创建表的过程中创建主键，创建主键就会自动生成主键索引树。
create table test1 (id int primary key, name varchar(10));

#在表创建完毕之后，创建主键
create table test2 (id int , name varchar(10));
alter table test2 add primary key(id);


#非主键索引
#在创建表的时候创建唯一索引与普通索引
create table test (id int primary key auto_increment, name
varchar(10), age int, unique index idx_age(age), index
idx_name(name));

#在创建表之后，创建唯一索引
alter table test2 add unique index idx_name(name);
create unique index index_name on test3(name);

#在创建表之后，创建普通索引
create index index_age on test3(age);

#在创建表之后，创建联合索引
create index index_age_name on test3(age, name);

#显示创建的索引
show index from test3;

#删除索引
alter table test3 drop index index_age;
drop index index_age_name on test3;
```
## 3.5：索引延伸问题
### 3.5.1：最左前缀法则
- 对于<font color="#ff0000">组合索引而言（也就是由多个列合在一起作为的索引）</font>，如果要使用组合索引进行查询的时候，一定要出现最左边的列，如果没有出现，那么就使用不到索引；只有在最左边的列出现的情况下，在出现后面的列才能使用到索引；

- 假设你创建了联合索引 `(name, age, city)`：
- ✅ **能用到索引**：`WHERE name = ...`（用到了第一列）。
- ✅ **能用到索引**：`WHERE name = ... AND age = ...`（用到了前两列）。
- ✅ **能用到索引**：`WHERE name = ... AND age = ... AND city = ...`（用到了全部）。
- ❌ **用不到索引**：`WHERE age = ...`（因为跳过了最左边的 `name`，索引失效）。
- ⚠️ **部分用到**：`WHERE name = ... AND city = ...`（只用到了 `name`，`city` 因为跳过了 `age` 而失效）。
- **记忆口诀**：**“带头大哥不能丢，中间兄弟不能断。”**

```
非聚集索引：索引和数据是分开存放的。(MyISAM的主键，非主键满足)

//聚簇索引=聚集索引
//非聚簇索引=非聚集索引
```
2、Innodb表中不建立索引/没有主动设置主键, 为什么要有默认索引? 默认索引是什么?
```
在Innodb中没有索引行不行?
// 不行, 因为在InnoDB表中, 数据是依赖于主键索引组织的, 和主键索引强绑定到一起的, 没有主键索引在InnoDB就没法存储和组织数据

在MyISAM中没有索引行不行?
// 可以, 没问题; 因为在MyISAM中索引和数据完全分离的

假设我们没有给InnoDB建立主键索引, 会产生什么问题?
// InnoDB会自动生成一个6字节的不可见的ROW_ID的列, 作为默认的主键索引组织数据 (ROW_ID的列名为GEN_CLUST_INDEX作为索引 )
```
3、索引性能这么好，是不是一个表建立的索引越多越好？
```
索引越多越好?
// 不是
// 1, 索引比较占用内存
// 2, 如果索引比较多, 添加/删除/修改数据 都有可能导致索引结构变化, 效率急剧降低.
// (查找不会导致效率降低)
// 3, 并不是每一列都适合作为索引
```
4、什么列适合作为索引?
```
// 1, 重复度低的列 (如果重复度比较高, B+树作为一个根据大小比较确定延伸结点方向的数据结构, 就没办法有效的利用大小比较)

//2, 使用率高的列(作为条件) (如果使用率比较低, 那么这个索引不但没什么意义, 而且在数据的添加/删除/修改,也会导致这个索引结构变化, 需要重新构建, 反而降低sql运行效率)

//3, 该列的值不会频繁变化的列 (如果一个列有索引, 而且这个列经常数据变化, 就会导致索引结构经常变成/重构,导致效率降低)
```
