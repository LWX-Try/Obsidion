## 2：大端地址和小端地址
大端：低地址存高位，高地址存低位。
小端：低地址存低位，高地址存高位。
数据在<font color="#ff0000">本机存储的时候，采用的是本机字节序，本机字节序是小端法；</font>
数据在<font color="#ff0000">网络上进行传输的时候，采用的是网络字节序，网络字节序采用的是大端法。</font>
```
//用于测试电脑是大端还是小端。
int main()
{
    int num=0x12345678;
    char *ptmp=(char *)&num;
    printf("*ptmp=%c\n",*ptmp);
    
    return 0;
}

//大小端转换函数：
#include <arpa/inet.h>

//convert values between host and network byte order

//h：host，本机的意思。
//n：network，网络。
uint32_t htonl(uint32_t hostlong);
uint16_t htons(uint16_t hostshort);
uint32_t ntohl(uint32_t netlong);
uint16_t ntohs(uint16_t netshort);

// uint32_t: 无符号 int

## 3：点分十进制转换：要用结构体类型
对于IP地址的转换，将点分十进制的IP地址，从本机字节序，转换为网络字节序。
```
#include <sys/socket.h>
#include <netinet/in.h>
#include <arpa/inet.h>

//将一个点分十进制的IP地址字符串转换为网络字节序的32位整型数表示。
in_addr_t inet_addr(const char *cp);

//将一个点分十进制的IP地址字符串转换为网络字节序的32位整型数表示。
int inet_aton(const char *cp, struct in_addr *inp);

//将网络地址转换为点分十进制IP地址的字符串形式。
char *inet_ntoa(struct in_addr in);
```
例如：
将点分十进制（字符串），转化为网络IP（也就是大端存储），再将网络IP转换为点分十进制（字符串）
```
struct sockaddr_in

    sin_family; //地址类型: AF_INET (IPv4)

}

### 2.1：socket函数
socket函数：调用socket函数，创建一个socket通信端点。

```
int socket(
    int domain,      //协议:AF_INET (IPv4)、AF_INET6 (IPV6)....
    int type,        //套接字类型: SOCK_STREAM (TCP)、SOCK_DGRAM (UDP)....
    int protocol     //协议:IPPROTO_TCP (TCP)、IPPTOTO_UDP (UDP)...; 
                     //当protocol为0时，会自动选择type类型对应的默认协议。
);

// 返回值:是一个非负整数, 代表一个文件描述符，用于标识创建的套接字，并通过这个描述符进行后续的网络I/O操作。
```
1. 实际上，<font color="#ff0000">socket函数本质上是在内核态中创建一个对象</font>，这个函数会返回一个文件描述符。但是文件描述符指向的并不是通俗意义上的文件对象。
2. 在这个socket对象中，包含了网络通信所需要的各种信息和状态（地址族，类型，协议，地址）。
   除此之外，<font color="#ff0000">该对象还维护了两个极其重要的缓冲区，输入缓冲区（SO_RCVBUF）和输出缓冲区（SO_SNDBUF）</font>，这两个缓冲区分别用于临时存储从网络接受的数据和待发送到网络的数据。

### 2.2：bind函数
绑定地址：使用bind函数给socket端口绑定端口和IP。
```
int bind(
    int sockfd,                      // socket端点文件描述符
    const struct sockaddr *addr,     // 要绑定的IP地址和端口号
    socklen_t addrlen
    // 指定的addr代表结构体长度,确保bind函数可以正确解析给定的地址信息:sizeod(addr)
);
//返回值: 成功时返回0。失败返回-1

const struct sockaddr *addr参数: 该参数用于提供给socket端点IP和端口信息, 但是sockaddr是一个通用的地址结构，实际使用的时候还是要使用sockaddr_in (IPv4)，sockaddr_in6 (IPv6)。
```
1. 一般我们都是给服务端bind, 那么客户端也可以bind吗?
   正常来讲客户端不需要bind; 客户端不bind操作系统都会分配一个临时的随机端口, 这已经足够使用了。
   当然如果有特殊需求, 也可以对客户端进行bind, 用以指明发送和接收数据的IP和端口。
2. 服务端可不可以不bind?
   如果服务端不进行bind操作, 一般操作系统都会分配一个临时的随机端口以供使用, 但是从逻辑上完全没有任何意义, 不允许这样操作。
### 2.3：listen函数
设置监听: 使用listen函数对设置好端口和IP的服务端socket端点监听外部连接请求
```
int listen(
    int sockfd,     //socket端点文件描述符
    int backlog     //这个参数指定了套接字可以挂起的最大连接数
);
//返回值: 成功返回0, 失败返回-1
```
一旦启用了listen之后，操作系统就知道该套接字是服务端的套接字，操作系统内核就不再启用其发送和接收缓冲区(回收空间)，转而在内核区维护两个队列结构：<font color="#ff0000">半连接队列和全连接队列。</font>
注意：此时socket端点对象的<font color="#ff0000">输入缓冲区（SO_RCVBUF）和输出缓冲区（SO_SNDBUF）被回收</font>，<font color="#ff0000">同时创建了半连接队列（SYN队列）和全连接队列（ACCEPT）。</font>
- 半连接队列用于管理成功第一次握手的连接;
- 全连接队列用于管理已经完成三次握手的队列。
- backlog参数是用来设置ACCEPT的最大长度，给一个一般性的正数即可。
- 如果ACCEPT队列满了，那么服务器收到的任何，再发起的连接都会直接丢弃。
- 使用netstat -an命令可以查看主机上某个端口的监听情况。
   (eg: netstat -an|grep 12345)

### 2.4：connect函数
- **功能**：客户端向服务器发起连接请求。
- **底层发生了什么**：触发 **TCP 三次握手**：
    1. 客户端发送 `SYN` 包。
    2. 服务器回复 `SYN+ACK`。
    3. 客户端回复 `ACK`。
- `connect` 函数会**阻塞**，直到三次握手成功（或超时失败）才会返回。
```
int connect(
    int sockfd,                    // socket端点文件描述符
    const struct sockaddr *addr,   // 目标服务器的地址和端口信息
    socklen_t addrlen
    // 指定的addr代表结构体长度,确保bind函数可以正确解析给定的地址信息
);
// 返回值: 成功0, 失败-1
```
1. 客户端在调用connect可以不使用bind来指定本地的端口信息，这客户端就会随机选择一个临时端口号来作为源端口。
2. 调用connect预期是完成TCP建立连接的三次握手。 如果服务端未开启对应的端口号或者未监听，则只能收到一个RST回复，并且报错返回的内容 是"Connection refused"。
### 2.5：accept函数
accept函数，由用户端调用，用于从全连接队列中取出一个已经完成TCP的队列。
```
int accept(
int sockfd,//socket端点文件描述符

struct sockaddr *addr, 
//用来获取连接对端/客户端的地址信息。如果不需要对端的地址信息, 可设参数为NULL

socklen_t *addrlen
//用来获取addr结构体的大小。如果使用addr/非NULL,那么addrlen必须设置addr的大小/sizeof(addr); 如果addr是NULL，addrlen也必须是NULL。
);
// 返回值: 成功则返回一个新的套接字文件描述符,用于与客户端通信。失败返回-1。
```

- **功能**：从全连接队列中取出第一个已完成的连接。
  使用accept函数从服务端的socket端点的全连接队列中取出一个连接 
- - 如果全连接队列为空，`accept()` 会**阻塞**（进入 `TASK_INTERRUPTIBLE` 睡眠状态），直到有新的连接到来。
- 一旦取到连接，内核会**创建一个全新的套接字（`struct socket`）**，并返回一个新的文件描述符 `new_fd`。
- **关键点**：原来的 `sockfd` 依然在监听，只负责“接客”；返回的 `new_fd` 才负责“聊天”。

### 2.6：send和recv函数（read和write）
send和recv负责收发数据。（和read，write一样。）
send和recv只能读写socket套接通文字描述符，不能读写管道，文件对应的文件描述符。
```
ssize_t send(
    int sockfd,       //socket端点文件描述符
    const void *buf,  //指向要发送数据的缓冲区的指针
    size_t len,       //buf中数据的长度，以字节为单位
    int flags         
    //用于指定发送操作的额外选项: MSG_OOB(发送紧急数据)、
    //MSG_DONTROUTE(不经过路由器直接发送到本地网络上的目的地)...大多数情况下，
    flags参数设置为0。
);
// 返回值: 成功返回实际发送的字节数。失败返回-1。

ssize_t recv(
    int sockfd,           //socket端点文件描述符
    void *buf,            //指向读出数据存放的缓冲区的指针
    size_t len,           //buf的长度，以字节为单位
    int flags
    //定接收行为的标志位:MSG_PEEK(查看数据但不从系统缓冲区中移除)、
    //MSG_WAITALL(等待所有请求的数据才返回)...大多数情况下，flags设置为0。
);
// 返回值: 成功时返回实际读取的字节数。如果连接已经关闭返回0(对方close: 四次挥手)。
读取失败返回-1

```
1. <font color="#ff0000">send和 recv函数只是将数据在用户态空间和内核态的缓冲区之间进行传输。</font>
2. <font color="#ff0000">send时将数据拷贝到内核态并不意味着会马上传输，而是由操作系统决定根据合适的时机</font>，再由内核协议栈按照协议的规范进行分节发送。(通常缓冲区如果数据过多会分节成 MSS的大小，然后根窗口条件传输到网络层之中)
3. 对于发送和接收数据，<font color="#ff0000">使用read和write函数可以实现同样的效果(本质是相同的)</font>，相当于flags 参数为0。
4. send和recv的次数和网络上传输的TCP数据段的数量没有关系，多次的send和recv可能只需。
5. TCP是一种流式的通信协议，消息是以字节流的方式在信道中传输，这就意味着一个重要的事情， 消息和消息之间是没有 边界的。<font color="#ff0000">有可能多个消息会在一次传输中被发送和接收（江湖俗称"粘包"），也有有可能一个消息需要多个传输才能被完整的发送和接收(江湖俗称"半包")。要一次TCP段的传输。</font>
### 2.7：close函数
```
int close(
    int fd      // socket端点文件描述符
);
//返回值: 关闭成功返回0, 失败返回-1
```
1. 客户端或者服务器使用close函数关闭连接的时候, 可能还有数据留在发送缓冲区中未被发送, close操作会试图发送这些数据。
2. close函数给连接的对端发送FIN包用于断开连接的四次挥手, 等待连接的另一端也发送FIN包，并且本端回应ACK确认关闭。
3. 释放端口等资源。

另外：
    1. 具有阻塞性质的函数：`accept`、`connect`、`read`、`write` 都是阻塞的。
    2. 管道只能在同一台机器上的进程之间通信。
       而socket传输数据，是通过内核的TCP/IP传输的，数据会经过网卡，路由器，交换机，跨越物理网络。
       他们的底层驱动和数据网络完全不同。
    3. 三次握手：有客户端的connect（）函数完成。
       当你在客户端调用connect连接时，该函数会阻塞，内核自动帮你在后台完成三次握手。当握手成功的时候，connect返回；若失败（超时，拒绝），返回-1。
       在服务器端，没有专门的握手函数，都是内核在收到SYN时自动回复的。accept函数只是把全连接队列里面的，已经建好的连接取出来给你用。
       connect负责三次握手的发起和完成，中间过程由内核完成。
    4. 四次挥手：有任意一方的close（）触发。
       当服务器/客户端调用close时，内核协议开始执行四次挥手。
       close负责四次挥手的发起，其他流程有内核完成。

## 2：通信函数
1. socket（）函数的使用和TCP的使用是一样的，只不过socket函数的type改为SOCK_DGRAM。

```
ssize_t sendto(
    int sockfd,             //socket端点文件描述符
    const void *buf,        //指向要发送数据的缓冲区的指针
    size_t len,             //buf中数据的长度，以字节为单位
    int flags,   
    //发送操作的额外选项: 紧急发送、直发...大多数情况下，flags参数设置为0。
    const struct sockaddr *dest_addr, //要发送的目的地址的IP地址和端口号

    //指定的dest_addr代表结构体长度,确保bind函数可以正确解析给定的地址信息:sizeod(dest_addr)
);

// 返回值: 成功时返回实际发送的字节数。这个数值可能会小于在length参数中指定的数值，表示只有部分数据被发送。失败时，返回-1。
```

```
ssize_t recvfrom(
    int sockfd,                     //socket端点文件描述符
    void *buf,                      //指向读出数据存放的缓冲区的指针
    size_t len,                     //buf中数据的长度，以字节为单
    int flags,                      //接收行为的标志位, 默认0
    struct sockaddr *src_addr,      //用于存储发送方的地址信息
    socklen_t *addrlen
    //指定的src_addr代表结构体长度,确保bind函数可以正确解析给定的地址信息:
    &sizeod(src_addr)
);
// 返回值: 成功时，返回接收到的字节数; 失败时返回-1。
```
- <font color="#ff0000">和基于TCP的send和recv函数不同的是, 基于UDP的sendto和recvfrom函数携带了地址信息, 用于确定目的地址和获取接收的信息的来源地址。</font>
- 这也就意味着, 在使用UDP进行无连接的通信时, 因为没有建立连接的过程，所以必须总是由客户端先调用sendto发送消息给服务端，这样服务端才能知道对端的地址信息，从进入后续的通信。
- 在使用UDP进行无连接的通信时, 因为是无连接的, 所以客户端或服务端关闭, 对方无法直接感知。
- 需要注意的是类型和参数: socklen_t \*addrlen (非int) (socklen_t 本身是unsigned int)

# 四：IO多路复用epoll（非常重要，常考）
---
## 1：select的缺陷
1. select的最大限制是它支持的<font color="#ff0000">文件描述符数量有限(fd_set大小1024)</font>, 对于大型服务器来说可能不够用。
2. 每次调用select 时，都需要把整个文件描述符集合<font color="#ff0000">从用户空间(用户态)复制到内核空间(内核态)</font>，当在内核态检查完就绪,<font color="#ff0000">又需要把就绪描述符集合从内核空间(内核态)复制到用户空间(用户态)</font>。 随着监听集合大小增加，这个操作变得越来越低效。
3. select函数使用的时候，每次调用完select都需要重新设置文件描述符集合，这是因为在select中文件描述符集合的输入输出未分离，<font color="#ff0000">返回的fd_set会将未就绪的文件描述符清空。</font>
## 2：epoll特点
<font color="#ff0000">在处理大量并发网络连接时,只要少量活跃的情况，</font>epoll是专门为高性能网络服务器设计的，可以有效地管理成千上万的并发连接。
1. <font color="#ff0000">epoll没有对文件描述符数量进行限制。</font>(它会随着内存的增大而导致上限变化, 可以参考: /proc/sys/fs/file-max )
2. epoll函数创建的<font color="#ff0000">epoll文件对象常驻内核态</font>；并且在该对象内部实现中把监听集合和就绪集合拆开维护。其中<font color="#ff0000">监听集合使用红黑树，就绪集合使用线性表(其实就是个双向链表)。</font>
3. <font color="#ff0000">在内核态epoll只检测那些变为活跃状态的文件描述符就绪与否</font><font color="#ff0000">，而不是像select一样对需要监听的文件描述符集合进行轮询检测。</font>显著减少CPU的负担，提高应用程序的性能。
4. 当应用程序调用epoll_wait时，内核会检查这个就绪列表(双向链表)，然后<font color="#ff0000">将就绪列表复制到用户空间提供的缓冲区中</font>，以通知应用程序哪些文件描述符上的事件已经就绪。
![[epoll函数内核创立的过程.png|306]]
- <font color="#ff0000">文件描述符对象会常驻内核，并且在内核中有两个数据结构，一个是红黑树，负责存放监听的文件描述符；另一个是就绪链表，存放的是就绪的文件描述符，也就是用两个数据结构将监听的文件描述符与就绪的文件描述符分开了。</font>

## 4：触发模式
在epoll_wait 的两种就绪触发方式中： 
1. 一种是<font color="#ff0000">默认的水平触发方式</font>(Level-triggered)。
2. 另一 种是<font color="#ff0000">边缘触发模式</font>(Edge-triggered) 。
### 4.1：水平触发
- 水平触发是epoll的<font color="#ff0000">默认</font>工作模式。在这种模式下，<font color="#ff0000">只要被监视的文件描述符上有待处理的事件</font>，epoll_wait就会通知应用程序。
- 如果某个文件描述符变得可读，epoll_wait会通知你这个文件描述符可读，<font color="#ff0000">即使你没有一次读取完缓冲区当中存在数据 ，下一次调用 epoll_wait时还会再次通知你就绪</font>。
  这里的从缓冲区读取数据，缓存区是指的这个文件描述符所指向的对象里面的缓存，在内核里面。
4.2：边缘触发
- 边缘触发它只在文件描述符状态变化时通知应用程序，即从不可用变为可用。
- 边缘触发的设置, 是在<font color="#ff0000">epoll_ctl</font>的时候, 给struct epoll_event \*event参数的events设置EPOLLET。
4.3：非阻塞模式recv
- 为了让while循环读取的时候, 在读取完毕跳出循环, 我们可以把 recv从阻塞方法改为非阻塞方法。
```
ssize_t recv(
    int sockfd,
    void *buf,
    size_t len,
    int flags
    //接收行为的标志位:MSG_PEEK(查看数据但不从系统缓冲区中移除)、MSG_DONTWAIT(非阻塞状态)
);
// 返回值: 成功时返回实际读取的字节数。如果连接已经关闭返回0(对方close: 四次挥手)。读取失败返回-1
```
- 我们可以把flags设置为MSG_DONTWAIT, 即非阻塞状态。在这种模式下，如果在调用时没有可用的数据可读取，recv不会阻塞当前线程，而是立即返回-1。

- recv函数的第四个参数flags有如下一些值
1. MSG_DONTWAIT：也就是说设置了这个值，那么函数不会阻塞，会立马返回；
2. MSG_WAITALL：这个标志会让程序阻塞等待所有的条件满足之后才返回；
3. MSG_PEEK：将数据从对应文件描述符的缓冲区中拷贝出来，不会对缓冲区中的数据进行清理；
4. 0：如果flags为0，那么recv与read基本等价（前提条件是socket的文件描述符）。
![[fcntl函数.png]]
为什么使用while和非阻塞的recv去使用ET模式进行输出，而不是直接使用默认的LT模式进行输出？
- 因为在LT模式，只要接收缓冲区里面还有个字符没有读取完，epoll_wait就会立即唤醒你的进程。而在ET模式，当缓冲区从“空”变为“非空”时，只唤醒一次，哪怕这个文件描述符对应的缓冲区里面还有数据，epoll_wait也会假装睡觉，不理你。
- 使用LT的话，就可以大量减少epoll_wait返回的次数（减少用户态与内核态的切换次数）。显著提高性能。
<font color="#ff0000">注意：边缘触发一般配合while循环和非阻塞的recv使用。</font>
解决阻塞问题：
1. 使用非阻塞的recv。修改最后一个参数。
2. 使用fcntl进行设置。
